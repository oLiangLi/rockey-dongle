## 1. 先定"这个数用来干什么" —— 用途决定标定

| 候选用途 | 只有比值重要? | 对本提案的要求 |
| --- | --- | --- |
| **① 时间片预算 / 抢占粒度** (`limit_cycles` 决定一次 `Execv` 跑多久) | 是 (绝对量级无所谓) | 权重之间的**比例**要与真实核接近, 否则"除法密集的程序"会白拿 32 倍机器时间 |
| **② 执行代价契约** (头文件 66 行的注释: "**对于执行程序的代价 (以花费的时钟周期计算) 应该尽量与解释器下的结果相同, 不应该出现过于大的偏差**"; 且 "通常我们 mock 的输入按 **1 周期 == 1 纳秒** 标定 (1GHZ)") | 否 —— **必须物理标定** | 权重就是"这条指令在这个 1GHz 模型下花掉几纳秒" |
| **③ 确定性与跨路径一致** | 否 | 权重必须是指令类的**纯函数** (见 §4.3) |

**决定性论据 (把它从"偏好"变成"必须")**: 头文件自己规定 `rLANG_ERROR_YEILD` 的语义是 "**async.wait ... a0 指示其周期数**" —— 也就是说 **guest 程序可以按周期数申请挂起**。如果 `cyc_` 不是物理标定的周期, 那么 guest 的"睡 N 个周期"就无从解释; 而且 ② 的契约会被破坏: 转译执行路径 (将来接 LIMIT / 原生) 花的是真实周期, 解释器若按"条数"记账, 两者必然对不上。

⇒ **结论: 按 ② 物理标定 (1 拍 = 1 纳秒), 比值自然满足 ①**。这也正是"基础 1 拍 + 小量级附加(1…31)"的由来。

## 3. ✅ 已落地的权重表

**基础**: `inner_Execv` 循环顶的 `++hart_->cyc_` 就是"每条指令 1 拍"(与 `script.cc:1424` 的 `--cycles_` 完全同构, 因此**不动**)。下表全部是**附加**值, 合计 = 1 + 附加。

| 指令类 | 常量 | 附加 | **合计** | 为什么是这个数 |
| --- | --- | --- | --- | --- |
| ALU / 跳转 (`JAL`/`JALR`) / `LUI` / `AUIPC` / CSR 类 | — | 0 | **1** | 单发射、单周期; 1 拍 = 1 纳秒的基准; 无条件跳转不加惩罚 |
| **条件分支** (`BEQ/BNE/BLT/BGE/BLTU/BGEU`) | `kCycBranch = 1` | +1 | **2** | **用户裁定**: "条件分支还是额外给一个周期的惩罚比较好, **不分是否命中**" ⇒ 固定惩罚, 与数据无关、可预测 |
| `LB/LH/LW/LBU/LHU` (载入) | `kCycMem = 1` | +1 | **2** | 顺序核无 cache: 1 拍发射 + 1 拍访存 |
| `SB/SH/SW` (存储) | `kCycMem = 1` | +1 | **2** | 同上 |
| `MUL` | `kCycMul = 2` | +2 | **3** | 32×32→32 阵列乘法器 (比 ALU 贵, 比除法便宜得多) |
| `MULH/MULHSU/MULHU` | `kCycMulh = 3` | +3 | **4** | 32×32→64, 多一级 |
| `DIV/DIVU/REM/REMU` | `kCycDiv = 7` | +7 | **8** | **用户裁定**: "感觉除法给出的周期惩罚太高了, 它的值应该要小于 搬运两次寄存器 + 定义一个自定义的门调用的代价, 我觉得定为 8 比较合适" ⇒ 上限 **8 拍** (不是基 2 迭代的 32 拍; 相当于 radix-4/8 或带提前结束的除法器)。**附带好处**: 单条指令最坏代价从 32 拍降到 8 拍 ⇒ **调度粒度收紧 4 倍** |
| `FENCE` / `FENCE.I` | `kCycFence = 3` | +3 | **4** | 流水线/取指冲刷; 且 hook (`op_FENCE/op_FENCEI`) 本来就有宿主工作 |
| 门调用 (`op_GATE`) | `kCycGate = 3` | +3 | **4** | **用户裁定**: "门调用也许应该缺省 +3, 然后超过 4 的自己再加" ⇒ 解释器只收进门费, 更贵的门由门实现自己 `hart_->cyc_ += ...` |
| 世界魔数 (`op_HYPER`) | `kCycHyper = 1 << 16` | +65536 | **65537** | **用户裁定**: "`op_HYPER` 是一项非常大成本的调用, 基本会导致一次 rpc, 本次执行几乎肯定返回 `rLANG_ERROR_HYPER`, 直到 rpc 结果回来才会被唤醒" ⇒ 计**RPC 发起**开销; **等待不计** (等待不是 CPU 时间, 与头内 "SIGALRM 不受此限制" 同一口径) |

**刻意"不加"的一项 + 两条已裁定**:

1. **按地址区分内存代价** (RAM vs 设备区 vs ROM) 不加 —— 虽然最终内存映射是固定的、这么做仍可确定, 但它把"计价"与"映射"耦合; 设备/宿主操作的代价应该走**门实现**自己的档位。
2. ✅ **条件分支 = 统一 +1 惩罚** —— 先裁定"分支命中不加, 假装我们实现了一个 100% 的分支预测器", **随后改为**: "**条件分支还是额外给一个周期的惩罚比较好, 不分是否命中**" ⇒ 现在命中与不命中都是 **2 拍** (固定值, 仍然与数据无关, 因此不破坏 §4.3 的纯函数性)。**无条件跳转 `JAL`/`JALR` 不加** (它们走同一条取指路径; 若要一起加, 只需在 `case 0x6F`/`0x67` 各补一行 `kCycBranch`)。
3. ✅ **`op_GATE` 缺省 +3** (合计 4 拍), 真实成本由门实现追加 —— 既保证"门不是免费的", 又不让解释器去猜宿主延迟。

## 4. 必须同时定下的三条语义 (否则会静默算错账)

### 4.1 `cyc_` 的语义从"条数"变成"周期"

现状注释没有写, 实测 (基线, 见 §7) **所有指令都是 1**, 所以"条数"与"周期"目前数值重合 —— 一旦加权就不重合了。
⇒ 头里必须写明: `cyc_ = 本时间片已消耗的**周期**数 (不是指令条数)`; `cycles_ = 该 hart 一生累计 (64 位)`。原型已按此加注释 (P7)。

### 4.2 `limit_cycles` 是**预算下界**, 单步约定与超调上限

- 检查点在**指令边界** (`do { ... } while (cyc_ < limit_cycles)`) ⇒ 预算不可能精确到拍, 只能到"条"。
- `do-while` 保证**至少执行一条** ⇒ **`limit_cycles == 0` 与 `== 1` 都是单步**的既有约定**不受加权影响** (已实测: 一条 `div` 在 `limit=0` 下仍执行 1 条)。这条必须保住: 否则预算耗尽时程序会**零进度死循环**。
- **最大超调 = 能继续执行的单条指令的最坏代价 = 8 拍** (即 `DIV`) ⇒ 这是本 VM 的**调度粒度上限**, 宿主安排时间片时按这个量级留余量。实测: `limit=0` 跑 `div` ⇒ 执行 1 条, `cyc_ == 8`。
  - ⚠ **例外是 `HYPER`**: 它一次性记 `kCycHyper` (65536 拍), 但它的语义本来就是"**必然结束本次执行**" (返回 `rLANG_ERROR_HYPER` 挂起等 RPC) ⇒ 它不是"跑着跑着超调", 而是"本次调用到此为止"; 真正的等待时间由宿主/RPC 层决定, 不进 `cyc_`。
  - ✅ **DIV 从 32 降到 8 的直接收益**: 调度粒度收紧 4 倍 (时间片最多浪费 8 拍而不是 32 拍)。它同时满足"**内置指令必须比自定义门便宜**"这条计价原则 —— 完整的算式、推论与那处待确认的读法见 **§4.4**。
- `kConfigLimitCycles = 1<<20` (≈1.05ms) 是**单次调用的上限**, 不是程序总预算; 程序总预算由宿主用 `cycles_` 跨调用累加来管 (§5)。

### 4.3 权重必须是指令类的**纯函数**

不得依赖: 操作数 (含 `div` 除零 / `INT_MIN÷-1` 这些边界 —— **不早退**, 一律 8 拍, 实测)、地址 (见 §3 第 2 条)、宿主/平台/耗时测量。
理由: ① 头文件已有的"确定性"契约; ② §1 的用途 ② —— 转译路径要"与解释器结果相同", 只有静态权重才可能做到; ③ 可复现性 (同一程序两次运行 `cyc_` 逐条相同, 实测)。
⇒ **不要**为了"更真实"去做数据相关的早退: 那会让程序耗时成为输入的函数, 统计与预算都会变得不可解释。

### 4.4 ⭐ **计价原则 (用户 2026-09-16): 内置指令必须比"自己写一个自定义门"便宜**

> 用户原话: "**我们内置的指令应该小于自己实现个自定义的门的代价, 不然就没人用了**"。
> 用户补充 (同日): "**用自定义门会占用寄存器, 很不划算的, 不会有人真这样做**"。

这条原则解释了 §3 里 div 为什么要从 32 压到 8 (以及为什么所有权重都要克制): 如果内置指令比"guest 自己搬两次寄存器 + 调一个自定义门"还贵, **guest 就会全部绕道走门**, 解释器里辛苦做的指令实现 (和它带来的执行路径一致性) 就没人用 —— 计价表会反过来惩罚"用内置指令"这件正确的事。

**但它是一条"保险丝", 不是竞争关系** (用户补充的要点): 门调用**还要占寄存器**——参数搬运、被调方保存/恢复现场, 在 32 个寄存器的机器上这是**真正的稀缺资源** (比几拍时间贵得多)。所以**没有人会真的用自定义门去实现除法**这种基本指令; 门是给**重操作 / RPC (HYPER、ukey 交互)** 用的。⇒ 下面这个界只需要**成立**, 不需要精算。

**把它写成可检查的不等式** (规程九已断言, 改坏了会红):

```
内置代价  <  搬运两次寄存器 + 一次自定义门调用        ← 这是**最低**算式; 真实代价还要加上寄存器/现场占用
   ↓ (按本表的最低算式)
8 拍 (DIV, 内置里最贵的一档)  <  2 × (1 + kCycMem)  +  (1 + kCycGate) + 1
                              =  2 × 2 (两次经内存搬运)  +  4 (门缺省) + 1 (自定义必然再自加)
                              =  9 拍                                        ✓ 成立 (且真实余量更大)
```

- **推论 1: `DIV` 的 8 拍就是内置指令的全局上界** —— 以后给任何指令加权都不得越过它 (除非同时调整门费或搬运费; 规程九第二条断言就是在钉这件事)。
- **推论 2: 门的缺省费不能太低** —— 若把 `kCycGate` 降到 0, 界会掉到 5 拍, 多数内置指令都会失去吸引力。**门费与内置代价必须一起调**。
- **推论 3 (用户补充): 门不是"贵一点的替代品", 而是"要占地的重武器"** —— 这也是"内置指令集必须够用"的真正理由: 常用操作必须在解释器里便宜地做掉, 门留给那些**不得不跨世界**的事。
- ✅ **读法问题已关闭**: 上一版我在这里留了一句"若'搬运两次寄存器'指 `mv`(2 拍) 则界退化成 7, DIV 需 ≤6" —— 按用户上面的补充, **不必为此动数字**: 真实门替代方案的代价远高于最低算式 (寄存器 + 现场), `DIV = 8` 保持。断言里用的仍是保守的"经内存搬运"算式 (留更多余量)。

## 5. 分层计价: 解释器管指令, 门实现管操作 (同一个 `cyc_`)

```
guest 指令       解释器       +1 … +8              (已落地: kCycMem/kCycMul/kCycMulh/kCycDiv/kCycFence)
                                   +65536            (kCycHyper: 世界魔数的 RPC 发起开销, 等待不计)
     |            (inner_Execv)
     +-- 门调用 -> 解释器缺省 +3 (kCycGate, 进入即计费)
                   门实现 (宿主/ukey) 再追加它自己的真实成本  (hart_->cyc_ += ...)
```

- **实现方式 (已实测, VM 端只需 `protected` 的 `hart_`)**: 门/宿主操作的真实成本由**门实现**自己追加 —— 它的量级由该操作的真实成本决定 (**不**参照 LIMIT 的数值, 见 §2)。
- **好处**: ① 一个账本同时装 guest 指令与宿主操作 ⇒ 时间片/总预算对"重操作程序"是公平的; ② 门**缺省**不是免费的 (+3), 但又不必让解释器猜宿主延迟; ③ 设备真实延迟变化时只需改门实现, 不动解释器。
- **溢出分析**: `cyc_` 是 `uint32`, 单次调用上限 `1<<20`, 单笔门费用建议 ≤ `0x100000` (与 `kCyclesExternal` 同档) ⇒ 单次调用内 `cyc_` 的量级 ≈`limit + 单笔最大费用` ≪ 2^32 ✓ 无溢出风险。**但**若某门要按字节计价 (如 `64 * size`, 64K 缓冲 ⇒ 4M 拍), 请在门里先做饱和/钳制, 或改由宿主按"字节数 × 单价"分次结算。
- ⚠ **一个已存在的记账细节 (实测发现, 建议写进注释)**: `cycles_ += cyc_; cyc_ = 0;` 发生在 `inner_Execv` 的**入口** ⇒ 返回时**最后一片尚未结算**。实测: 三次 `limit=1` 调用 (1+2+3 拍) 之后 `cycles_ == 3` 而 `cyc_ == 3` ⇒ **总代价 = `cycles_ + cyc_`**。宿主做程序总预算时**必须把两者相加** (或让 VM 提供一个 `TotalCycles()` 小工具), 否则会少算最多一个时间片。

## 9. 顺带发现 (就在你要改的同一段代码里, 都已实测)

### 9.1 `lw x0, addr` 不访存 —— 违反 ISA 卷 I §2.6 (**✅ 已修**, blob `bf3d9f5a`)

**规范原文** (离线 PDF = Volume I v20260120, §2.6 Load and Store Instructions, p.33):

> "Loads with a destination of x0 **must still raise any exceptions** and cause any other side effects even though the load value is discarded."

**现状**: `case 0x03 >> 2` 用 `if (0 != rd) { ... }` 把**整个访问**包了起来 ⇒ `rd == 0` 时既不访存也不报错。**对照实验** (同一地址, 只有 `rd` 不同):

```
lw  x0, 0(x0)   [rd=0, 地址 0 未映射]  =>  rc = TIMEDOUT  (静默"成功")
lw  t0, 0(x0)   [rd=5, 同一地址]       =>  rc = SIGSEGV   (11)   ← 应该两边都这样
lb  x0, 0(x0) / lbu x0, 0(x0)          =>  rc = TIMEDOUT  (同样静默)
```

**影响**: ① 不符合 ISA; ② 与本仓自己的 fail-closed 取向不一致 (`mm_CHKWR/RO/CS` 连 `size == 0` 都拒绝非法地址); ③ `lw x0` 作为"探针"不可信 (ISA 特意保证它可以用来探测可访问性); ④ 在最终内存映射下, `lb x0, 0` 这类对未映射区的访问**不会**报错, 少了半个护栏。
**为什么不能简单去掉 `if`**: 落点不能写 `regs[0]` —— **x0 是执行循环的错误通道** (`while (regs.zero == 0)`), 载入结果会破坏它。⇒ 修法是 `reg_t dummy; reg_t* const dst = rd ? &regs[rd] : &dummy;`, 让访问照常发生, 结果丢进临时寄存器 (P2 已落地, **规程九 ⑥** 验证: `lw x0,0(x0)` 报 `SIGSEGV` 且错误只落在 x0; `lw x0,0(t1)` 合法地址仍计 2 拍且 x0 未被写坏)。

### 9.2 `DIV` 的 `-rs1` 在 `rs1 == INT_MIN` 时是**有符号溢出 UB** (**✅ 已修**, blob `bf3d9f5a`)

`case 4: // DIV` 的快速路径 `regs[rd].iv = -regs[rs1].iv;` 恰好就在处理 `rs2 == -1` 的情况, 而 `INT_MIN` 除以 `-1` 正是 ISA 规定的**溢出特例** ⇒ 这条路径**专门会**执行到 `-INT_MIN`。C++ 里对 `int32_t` 取负溢出是 UB (与仓内"代码必须消除潜在的 UB"的注释相悖, 也与 `rLANGiOPT` 的 `-O3` 属性叠加)。
**修法 (P6)**: `regs[rd].uv = 0u - regs[rs1].uv;` —— 无符号回绕有定义, 结果与 ISA 要求完全一致 (`INT_MIN` 仍是 `INT_MIN`), **规程九 ⑦** 已验证。
