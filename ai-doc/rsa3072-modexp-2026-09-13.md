# RSA-3072 设备内模幂(mod_exp)—— 可行性、OpCode 落地与真机实测 2026-09-13

> 承接 `ai-doc/rsa3072-device-generation-2026-09-11.md`(设备内单指令生成整对 1536 位素数,52.1 min)。
> 本文回答下一个问题:**3072 位模幂在 ukey 的栈/内存约束下是否可行**;结论是可行,并已实现为
> **普通 OpCode**(`ExRSAModExp`),由 host 注入正确的 N/E/D 完成 RSA3072 端到端验证。
> 分支:master(Windows 主工作区);代码:`Interface/modexp.{h,cc}`、`Interface/script.{h,cc}`、
> `src/__Testing__/__dongle__/main.cc`(index 20)、`src/__Testing__/__rsamodexpvm__/`。

## 1. 结论

| 问题 | 结论 |
|---|---|
| 3072 位 mod_exp 在设备约束下可行? | **可行**。栈最深链 **≈1.34KB ≤ 2032B**,工作区全部走 InOutBuf/ExtendBuf,固件 `.bss` 仍 16B、无 `.rodata` |
| 实现形态 | **普通 OpCode** `kExRSAModExp = 0x150`(`argc : 6`),未退化为 `OpExecute_*` |
| 设备内 3072 位私钥运算耗时 | **238.4 / 239.7 / 241.1 / 241.4 s ≈ 4.0 min**(4 次真机实测,`beats` 384–386) |
| 设备内 1024 位私钥运算耗时 | **9.36 s**(同一条指令,`bits=1024`,beats=128) |
| 正确性 | 设备 `s = m^d mod N` 与 TASSL `BN_mod_exp` **逐值一致**;host 独立复核 `s^e == m` 通过;设备内验签 `m2 == m` 通过;GuardBytes 完好、`mainRet=10086` |
| 复用成熟的 MR Montgomery? | **算法同源但不复用代码**:`mr.cc` 的 CIOS 临时区按 k≤48 定死,3072 位(k=96)时 BN 的 96 limb 已无进位余量 ⇒ 新写"缓冲区全部由调用方提供"的一份(见 §2) |

## 2. 实现:`Interface/modexp.{h,cc}`

```cpp
class RsaModexp {
  static constexpr int kMaxWords = 96;        /* 3072 bits */
  struct Workspace { limb_t t[98]; limb_t acc[96]; };   /* 776B, 调用方提供 */
  static void MontMul(limb_t* r, const limb_t* a, const limb_t* b, const limb_t* n, int k, uint32_t n0inv, limb_t* t);
  static void ToMont(limb_t* a, const limb_t* n, int k);
  static void FromMont(limb_t* a, const limb_t* n, int k);
  int ModExp(limb_t* out, const limb_t* base, const uint8_t* exp, int expBytes,
             const limb_t* n, int k, Workspace& ws);
};
```

要点:

1. **CIOS 与 `mr.cc` 同算法**,但临时区 `t[k+2]` 由调用方给出 ⇒ 栈上只留帧
   (arm `.su`: `MontMul` 136B、`ModExp` 64B、`ToMont` 48B、`FromMont` 64B、`KickWDG` 16B)。
2. **就地/别名安全**:`r` 可与 `a`/`b` 别名(结果经局部 `t` 回写);`out` 可与 `base` 别名
   (先把底数复制进 `ws.acc`);`out` 不得与 `exp` 重叠。
3. **定长 k limb**:`ToMont` 的倍增进位被丢弃后按定长减法补偿(`a_low - n mod 2^{32k}`),
   `FromMont` 的半减把最高进位重新塞回 `a[k-1]` —— 两者都不需要第 `k+1` 个 limb 的存储。
4. **左到右二进制幂**从 `r = base` 起步,**必须剥掉指数的前导 0 比特**(最高非零字节内的
   那些):否则结果会变成 base 的错误幂次(本轮实测踩坑,见 §5.1)。
5. 每 `kKickSquarings = 8` 次平方一次 `KickWDG()`(LED 反转 + `GetTickCount` COS 心跳;
   设备 `GetTickCount` 在 item 执行期不自走,但作为"触发一次 COS"足够)。3072 位私钥运算
   实测 `beats ≈ 386 ≈ 3072/8`。
6. 大数一律**小端 32 位 limb**(与 `BN::v`、dashboard 落盘同序);指数以**小端字节数组**给出,
   允许前导零字节(`e=65537` 只有 3 字节 ⇒ 只算 17 位)。

## 3. OpCode 接口:`kExRSAModExp`

```cpp
kExRSAModExp = 0x150,   // argc : 6, value = ExRSAModExp(nFile, nOffset, mAddr, outAddr, expAddr, bits)
```

| 参数 | 含义 |
|---|---|
| `nFile`, `nOffset` | 模数 N 所在**数据文件** id 与偏移(小端 `bits/8` 字节) |
| `mAddr` | 底数 m 在 VM 数据区(data_ 0..1023)的偏移 |
| `outAddr` | 结果 s 写回偏移(3072 位时建议 == `mAddr` 原地覆盖) |
| `expAddr` | 指数(小端 `bits/8` 字节)在 VM 数据区的偏移 |
| `bits` | 1024 / 1536 / 2048 / 3072(32 的倍数) |

- **为什么模数走数据文件**:VM 数据区只有 1KB,3072 位时 `N(384B) + m(384B) + 指数(384B) = 1152B`
  装不下;模数是设备常驻量(N 与 ROOT CA 私钥同源),底数/指数/结果留在数据区即可
  (`384 + 384 = 768B`,原地覆盖)。这也与"CA 私钥常驻设备"的生产形态一致。
- **地址必须 4 字节对齐**(按 limb 直接寻址,与 `LoadMM/StoreMM` 同规),否则 `zero_ = SIGSEGV`。
- `nFile < 1000` 需要管理员权限(与 `kReadDataFile` 同规)。
- 工作区复用 `buffer_`(设备侧 ExtendBuf)+ 栈上 384B 模数缓冲 ⇒ 不需要新增全局/静态存储。
- DSL 侧名字为 `ExRSAModExp(...)`:由 `Interface/script.h` 经
  `node tools/rockey/LIMIT/script/opcode.cjs` 自动生成到 `Web/Script/lib/opcode.ts`
  (OpCode 155 / AllFunc 96)。

## 4. 验证

### 4.1 host 自测(mode 4,`__Testing__dongle__ -0 14 4 C00`)

- `ToMont(2) == 2R mod N`(TASSL 对照)、`MontMul(2R,3R) → 6`、原地平方 `(2R)² → 4`;
- `2^10 = 1024`、`3^5 = 243`;`ToMont/FromMont` 往返;
- **随机对拍 TASSL**:`MontMul×3` + 小指数 `ModExp×2`(指数 1..64 位,专打前导零比特);
- 3072 位 `m^d mod N` 与 `BN_mod_exp` **MATCH**(host 60–163 ms);RSA 自洽 `(m^d)^e == m`;
- 复核路径自检:用与真机判定**同一段代码**验证 host 自己算出的 s。

### 4.2 真机(`__Testing__dongle__ -2 14 <mode> <bits>`)

| 运行 | 模式 | bits | 设备耗时 | beats | 设备 s == TASSL m^d | 独立复核 s^e==m | 设备内验签 m2==m |
|---|---|---|---|---|---|---|---|
| 1 | 1 | 3072 | 238,384 ms | 384 | ✓ | ✓(事后 mode 5) | — |
| 2 | 2 | 3072 | 239,654 ms | 385 | ✓ | ✓ | ✓ |
| 3 | 1 | 3072 | 241,052 ms | 384 | ✓ | ✓ | — |
| 4 | 2 | 3072 | 241,411 ms | 386 | ✓ | ✓ | ✓ |
| 5 | 1 | **1024** | **9,359 ms** | 128 | ✓ | ✓ | — |
| 6 | 2 | 3072 | 241,678 ms | 386 | ✓ | ✓ | ✓ |

第 6 次(mainRet 判定修正后)完整判定:**`sign(s^e==m)=1 ref(s==m^d)=1 verify=1 => PASS`,进程 exit 0**。
每次都是**单条 `ExecuteExeFile`** 内完成:`mainRet=10086`(0 错误)、`GuardBytes error=0`、
设备状态 `magic=4d585053('MXPS') bits=3072 sign_rc=0 verify_rc=0`。

> 耗时与模型吻合:1024 → 3072 的比值实测 ≈25.6,理论 `(96/32)² × (3072/1024) ≈ 27`。

### 4.3 opcode 层(模拟器,`__Testing__rsamodexpvm__`)

直调 `VM_t::OpFuncRSA(kExRSAModExp, …)`:3072 位签名/验签、1536 位签名全部 **MATCH TASSL**;
错误分支:argc=5 → `SIGILL`、非对齐地址 → `SIGSEGV`、`bits=1000` → `-EINVAL`、
不存在的模数文件 → `-EIO`。退出码 10086(0 错)。

### 4.4 门禁

- `make dongle`:固件默认**不再随机填充**(rockey_dongle.bin 56,640B / RockeyTrust.bin 55,872B;发布构建 `rLANG_ROCKEY_CONFIG_RELEASE=true` 时仍为 65,520B)、`.bss` **0x10**、**无 `.rodata`**;
- `make rockey-stack-check`:稳态最大 **1928B ≤ 2032B**(0 条超预算;最深仍是 `PrimeMRTests` 链);
  单独核算本改动:opcode 路径 `Start 376 + VM_t::Execute 48 + OpFuncRSA 712 + ModExp 64 + MontMul 136 ≈ 1336B`,
  测试路径 `Start 144 + Testing_RsaModexpTests 832 + 64 + 136 ≈ 1176B`;
- `node tools/rockey/LIMIT/ci/run-ci.cjs`:**8/8 PASS**(jsuite/mkey/skey/emuadmin/corpus/pkeyself/x509ext/trngfail)。

## 5. 踩坑记录(后续务必先读)

### 5.1 左到右二进制幂的前导 0 比特(算法 bug,已修)

首版 `expBits = 最高非零字节 × 8`,而算法以 `r = base` 起步(隐含最高位 1)。指数最高字节
常带前导 0(实测 d 的最高字节多在 0x20..0x7F)⇒ 多算若干平方,结果变成 base 的错误幂次。
**现象**:`2^10` 算出 0、`3^5` 算出随机数、3072 位 `m^d` 与 TASSL 不一致;
自检里 `ToMont`/`MontMul`/别名平方却全部正确 —— 因为它们是单步调用,不经过循环。
**修法**:逐比特剥掉前导 0(`while (n > 1 && !bit(exp, n-1)) --n;`),并加"小指数随机对拍"用例。

### 5.2 设备 `Start` 会覆写 `Context->result_[0]/[1]`,且 `mainRet` 的"0 错"是 **10086**

- 设备端 `Start` 在测试项返回后执行 `Context->result_[0] = result; Context->result_[1] = result2;`,
  而 `result` 是它自己的累加值(含 `GetExpireTime` 等 `NOTIMPL` 负值)⇒ **host 读这两个字段得到的
  与本次模幂无关**。规则:设备端执行状态一律写 dashboard(本轮用
  `ModExpStatus {magic,bits,sign_rc,verify_rc,heartbeats}`)。
- 设备 `Start` 返回的是 **`10086 - 错误数`** ⇒ **`10086` 才是"0 错"**。首版判定写成
  `0 == main_result`,于是"数学全对、判定全红",连续数轮误判 FAIL;修成 `10086 == main_result` 后
  同一次运行立刻 PASS。**凡是 host 侧判定设备返回, 先确认这两个约定。**

### 5.3 长寿命 `BN_CTX` 上的 `BN_mod_exp` 在长设备调用后给出错值(未完全定因)

现象:同一份输入(见 §4.2),用**复用**的 `BN_CTX` 调 `BN_mod_exp(chk, s, e, N, ctx)` 在 3072 位下
得到不等于 m 的结果;改用**新建** `BN_CTX` + 从 dashboard 字节重建的 BIGNUM 则正确
(1024 位时复用上下文也正确;多次复现,逐字节一致、`BN_cmp` 全 0,`rc` 均为 1)。
**现状**:判定口径已改为"独立复核(新建上下文 + dashboard 字节重建)",真机全绿;
**待查**:是 TASSL 的 `BN_CTX` 状态问题还是厂商 DLL 长调用期间的宿主内存影响 ——
后续可用"设备调用前后各跑一次同一 `BN_mod_exp` 并比对"的独立用例定因。

### 5.4 其他工程坑

- **Windows 日志捕获**:`platformLoggingWrite` 走 `WriteConsoleW(stderr)` + `OutputDebugStringW`,
  一旦 stdout/stderr 被重定向/管道捕获就**什么都收不到** ⇒ 本轮给
  `__Testing__dongle__`/`__Testing__rsamodexpvm__` 的 host `main()` 加了 `WT_RKEY_LOG=<path>`
  (`rlLoggingOutputFile`),`make`/CI 下也能留痕。
- `s_host` 是 **winsock `in_addr.h` 的宏**(`S_un.S_un_b.s_b2`)⇒ 变量名冲突,改名 `s_mine`。
- Windows 构建需 **vcvars64 + cygwin make**(clang-cl/link.exe 在 VS 目录下):
  `cmd /c ""…\vcvars64.bat" && C:\cygwin64\bin\make.exe windows -j8"`。
- 设备侧大缓冲(~1.2KB)只用于**测试项**;正式 opcode 路径的栈上只有 384B 模数缓冲。
