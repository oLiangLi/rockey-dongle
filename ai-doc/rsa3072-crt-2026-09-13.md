## 1. 结论

| 项 | 全宽 `ExRSAModExp` | **CRT `ExRSACrtModExp`** |
|---|---|---|
| 设备内 3072 位私钥运算 | 238-242 s ≈ 4.0 min | **61.7-62.1 s ≈ 1.0 min**(**3.9×**) |
| MontMul 宽度 | k=96(3072 位) | k=48(1536 位)×2 ⇒ 单次代价 1/4 |
| 指数位宽 | d(3072 位) | dmp1/dmq1(各 1536 位) |

## 2. 完整私钥 blob(落盘布局)

`RsaModexp::KeyBlob`(小端, 定长, `Interface/modexp.h`):

```
偏移                字段                     长度
[0,  16)            header{magic 'RSAK', bits, flags, 0}
[16, +w)            n                         w = bits/8
[.., +w)            e(小端, 高位补 0)         w
[.., +w)            d                         w
[.., +h) × 5        p, q, dmp1, dmq1, iqmp    h = w/2
flags bit0 = 含 CRT 参数(p/q/dmp1/dmq1/iqmp 可用)
```

3072 位: `w=384, h=192` ⇒ **总长 16 + 3×384 + 5×192 = 2128B**;2048 位为 1424B。
字段含义: `dmp1 = d mod (p-1)`、`dmq1 = d mod (q-1)`、`iqmp = q^{-1} mod p`。

**导入方式**:
- 测试:host 用 TASSL 生成完整私钥 → 按上述布局写入 dashboard(`kFactoryDataFileId`,测试用 `[1024, 3152)`);
- 生产(建议):**必须**用 `KDF(MASTER.SECRET, nonce, kType)` + AEAD **密封**后落盘(见
  `ai-doc/rsa-root-ca-generation-2026-09-11.md`);脚本侧可用现成的 `WriteDataFile` 分块导入
  (数据区 1KB,blob 2128B ⇒ 6 次 384B)。
  注意(2026-09-13 实测 + 设计说明, 见 `ai-doc/admin-file-permission-2026-09-13.md`):设备数据文件
  `id < 1000` **只限制建/写/删, 不限制读**(设计前提是"任何已存在的文件必然可被读出, 不信任 COS 承诺")
  ⇒ **不能**把"放进 id<1000 文件"当成对私钥的机密性保护;机密性一律来自 `KDF(MASTER.SECRET, nonce, kType)`:
  `kType == 0` 的结果**只在当前 ukey 有效**(混入本机 `LocalChaos`/`GetDongleInfo`), `kType != 0` 则
  **共享 MASTER.SECRET 的所有 ukey 都能复现**(只用世界级常量)；密文放可读位置是否安全取决于选哪种。

## 3. 新增指令(普通 OpCode)

```cpp
kExRSACrtModExp = 0x151, // argc : 5, value = ExRSACrtModExp(keyFile, keyOffset, mAddr, outAddr, bits)
kExRSAKeyCheck  = 0x152, // argc : 4, value = ExRSAKeyCheck(keyFile, keyOffset, scratchAddr, bits)
```

- `ExRSACrtModExp`: 从 blob 取 p/q/dmp1/dmq1/iqmp,算
  `s_p=(m mod p)^dmp1 mod p`、`s_q=(m mod q)^dmq1 mod q`、`h=(s_p-s_q)·iqmp mod p`、
  `out = s_q + q·h`(= m^d mod n,且天然 < n,无需再取模)。结果区**兼作 p*q 的乘积缓冲** ⇒
  **要求 `outAddr != mAddr`**(与全宽版"可原地覆盖"不同);`bits ∈ {2048, 3072}`,地址 4 字节对齐。
- `ExRSAKeyCheck`: 只校验不动数据 —— magic/bits/flags、`p*q == n`、`q·iqmp ≡ 1 (mod p)`、
  `dmp1 < p-1`、`dmq1 < q-1`;`scratchAddr` 需 bits/8 字节。**建议导入后先跑一次再签名**。
- `ExRSACrtModExp` 自身也会先做前两项校验(失败返回 `-EBADMSG`),密钥被换/损坏不会静默签错。
- DSL 名字: `ExRSACrtModExp(...)` / `ExRSAKeyCheck(...)`(`opcode.ts` 已重新生成: OpCode 157 / AllFunc 98)。

## 4. 实现要点(`Interface/modexp.{h,cc}`)

1. `ModReduce(r, a, aWords, n, k)`: 逐位 shift-subtract 求 `a mod n`(2k→k limb),约 32·aWords·k
   次操作(k=48 时 ≈15 万次,设备上可忽略);用于 `m mod p`、`m mod q`、`q mod p`。
2. `HalfModExp(out, base, exp, n, k, t)`: 半域模幂,**base 就地进 Montgomery 域**(因此不需要
   全宽版的 `Workspace::acc` 槽,省 k 个 limb);要求 `out != base`。
3. `CrtCombine(out, s1, s2, p, q, iqmp, k, tmp, t)`:
   `tmp=(s1-s2) mod p` → Montgomery 域乘 `iqmp` → 出域得 h → `out = q*h + s2`(`MulAddK`)。
   `tmp` 允许与 `s1` 同一缓冲(逐 limb 读写)。
4. `CrtWorkspace` 只留 `{a,b,c,t}` = **776B**,与全宽 `Workspace` 同尺寸:
   `a`:p→q;`b`:dmp1→dmq1→q→iqmp;`c`:m mod p/q、半宽校验缓冲、重组临时。
   两个半域结果 `s1/s2` 直接写**栈**上(2×kHalfWords = 384B),不占工作区。
5. 心跳: 每 8 次平方一次 `KickWDG`;实测 `beats=384`(= 2×(1536/8))。

### 5.3 为什么是 3.9×?—— 与"乘法复杂度"的关系(2026-09-13 追加)

CRT 相对全宽的提速上限 ≈ `cost(半域 MontMul) / cost(全宽 MontMul)`
(指数位宽减半与"要算两次半域幂"相抵, 只剩单次乘法的宽度差):

| 乘法实现 | cost(48 limb)/cost(96 limb) | 预期 CRT 提速 | 备注 |
|---|---|---|---|
| 朴素 schoolbook **O(k²)**(本实现) | **(1/2)² = 1/4** | **4×** | 实测 **3.87–3.89×**, 与朴素乘法完全吻合 |
| Karatsuba **O(k^1.585)** | (1/2)^1.585 ≈ 0.33 | ≈3.0× | |
| Toom-3 | (1/2)^1.465 ≈ 0.36 | ≈2.8× | |
| FFT/NTT **O(k log k)** | → 1/2 | **→ 2×** | 业界经验: 3072 位规模还不到 FFT 的甜点区 |

⇒ **3.9× 不是"我们的 Montgomery 特别快", 而是"我们的乘法特别朴素"**: 用户此前在带次二次
乘法(或窗口法)的实现上测到的 **2.5×** 才是那个算术层级的正常值。真正被朴素乘法拖累的是
**绝对耗时**(全宽 4.0 min / CRT 1.0 min 都还有很大压缩空间)。

**要把绝对时间做下来, 需要注意两点**:

1. CIOS 把"乘"与"Montgomery 约减"交织在一起(各 k² 次乘加)。只把乘积换成 Karatsuba 只优化了
   一半, 约减仍是 O(k²)。要真正受益得改成"**先算 2k 位乘积(Karatsuba/Toom) + 再做 Montgomery
   约减**", 需要额外一块 2k limb 缓冲(全宽 768B / 半域 384B, 当前工作区没有余量), 并重排
   `r`/`a`/`b` 的别名策略。在 96 limb(3072 位)规模预估 **1.3–1.7×**, 不是量级提升。
2. **滑动窗口指数**(减少乘法次数 1.5x→1.2x)受 RAM 限制: 半域 w=4 需 8 个预计算点
   (8×192B = 1.5KB)、全宽 w=4 需 3KB, 而设备可用 RAM 只有 InOutBuf 1KB + ExtendBuf 1KB
   (+2032B 栈)。w=2(3 个点 = 576B/1.15KB)可行但收益 ~10%。
3. FFT/DFT 在 3072 位规模不划算(通常 >8k–16k 位才起步), Cortex-M0 无 FPU/大寄存器, 多倍长
   NTT 的常数开销会吃掉收益; 现实选项是 **Karatsuba / Toom-3**。

**结论**: 若目标是缩短绝对时间, 值得做 Karatsuba/Toom(预计 4.0 min → ~2.5–3 min、
1.0 min → ~0.7 min); 比值会同时从 3.9× 回落到 ~2.5–3×, 属预期。

## 6. 与全宽版本的分工

- **CRT(0x151)**: 私钥运算(签名/解密)的默认路径,快 3.9×;需要完整私钥(含 CRT 参数)。
- **全宽(0x150)**: 只有 (n,e) 或只需要 `m^e mod n` 的场合(验签、公钥运算)、以及 1024/1536 位
  密钥(CRT 的半个模数会小于 `kMinWords`,故 CRT 仅支持 ≥2048 位)。
- 两者结果**逐字节一致**(已实测),可互为交叉验证。
