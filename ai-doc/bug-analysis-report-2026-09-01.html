03致命级问题(Critical,4 项)

CriticalC-01脚本语言与VM · 设备端
脚本摘要指令空指针写入 —— 匿名脚本可将设备打死
Interface/script.cc:856-869(VM_t::OpFuncDigest,SHA1/SM3/SHA256/SHA384/SHA512 共 5 处)
问题
OpCheckMM 在 addr+size > 1024 时只置 zero_ = SIGSEGV 并返回 nullptr,但 zero_ 要到 Execute() 循环顶部才被检查——当前这条指令仍会继续执行,md == nullptr 被直接传入哈希函数并写入摘要。同文件其它 handler(如 kRandBytes、SM4/TDES)都做了 if (p) 检查,唯独 digest 五处全部遗漏。
触发条件
匿名脚本执行 kExDigestSHA256 且栈参数为 [input_addr, size, 1000](1000+32 > 1024)。kScriptAtomic 无需任何签名——MAC 密钥 = SM3(ScriptText 前 224 字节)可自行计算,即任何能向设备提交 1024 字节 InOutBuf 的人都能触发。
后果
MCU 上向地址 0x00000000 写 20~64 字节(向量区,写只读区 → BusFault/HardFault,设备挂死,拒绝服务);主机/模拟器构建上直接 NULL 写段错误。
修复:五处 digest handler 增加 if (md) 检查(nullptr 时立即 return);更彻底的做法是把"检查 zero_ 后再执行"统一进指令分发层。
CriticalC-02密码学原语
crypto.cc 严格别名违规 —— -O2 下 X25519/Ed25519 静默输出错误且非确定(已实证)
base/src/crypto.cc:24-151(cipher_memset / cipher_memcpy / cipher_memmove 及 146-151 行的宏重定向)
问题
自实现的 cipher_memset/cipher_memcpy 用 8 字节 long 类型左值读写调用方缓冲区,而调用方对象是 int32_t fe[10] 等不同类型——违反严格别名规则;cipher_memcpy 还声明 __restrict。146-151 行把文件内所有 memset/memcpy/memmove 宏重定向到这些实现,命中 fe_copy、fe_0/fe_1、x25519_scalar_mult_generic 的标量拷贝等核心路径。
实证结果
在本机 aarch64 GCC 11.4.0(与项目交叉编译器同版本):-O1/-Os/-O3 全部测试正确;-O2 下 X25519 对 RFC 7748 标准向量输出错误,且同一输入多次运行结果每次不同(读取未初始化栈内容);Ed25519 的 200/200 随机签名与参考实现全部不符、但 dongle 内部 sign/verify 自洽——可自验证却与一切标准实现不互操作,极难被发现。加 -fno-strict-aliasing 或删除宏重定向后 -O2 立即恢复正确,因果已隔离确认。
现状
当前构建 Build/Main.mk:60-61 release 默认 -O1、MCU 用 -O1/-Os,碰巧安全;但 Build/config/windows.conf:51-53 已配置 -O2,且构建标志用 ?= 赋值可被环境覆盖——换编译器版本或调整优化级别都会静默产出错误且非确定的共享密钥与签名。
修复:删除 146-151 行宏重定向改用 libc 内存函数(编译器本就会生成正确的向量化代码);或给字访问类型加 __attribute__((__may_alias__))。CI 必须增加"以 -O2 编译并跑 RFC 8032/7748/8439 向量"的门禁。
CriticalC-03主机侧接口
--list 命令栈缓冲区溢出约 1.4KB —— 可破坏返回地址
src/app/main.cc:652(char line[2048])· main.cc:674 → base/src/data.cc:89(rl_BASE64_Write 无边界检查)
问题
rl_BASE64_Write 无任何边界检查,输出为 ceil(n/3)*4+1 字节。kSizeTotal = count × 40(DONGLE_INFO),count 上限 64 → 最多 2,592 字节数据 → 3,457 字符写入 2,048 字节缓冲。
触发条件
接入 ≥38 只加密狗后运行 --list(37 只时已溢出 25 字节)。代码本身支持 80 只(main.cc:651),工厂批量插狗场景完全可触发,且溢出后 main.cc:675 的 sprintf 继续越界写。
修复:给 rl_BASE64_Write 加输出长度参数并在越界时返回错误;调用侧按最坏情况(count=64)分配缓冲。
CriticalC-04主机侧接口
rl_BASE64_Read(…, -1) 不在 NUL 处终止 —— 越界读 + 无界写
base/src/data.cc:49-87 · 调用点 src/app/main.cc:252(Utilities 的 ReadLine lambda)
问题
zLEN<0 时转 strlen 的逻辑被注释掉;循环中 NUL 映射为 -2 被"忽略非法字符"逻辑继续扫描,0 == zLEN-- 从 -1 递减永远不为 0,唯一出口是遇到 '='。
触发条件
在 --reset/--factory/--lock/--dashboard 的交互输入中粘贴不含 '=' padding 的 base64(或截断/错误数据):扫描器越过 128KB 的 sline_ 继续扫描后续栈内存,并无界解码写入 128KB 栈缓冲(main.cc:231-232)。正常带 padding 的输入不触发——典型的畸形输入内存破坏。
修复:恢复 zLEN<0 → strlen 的转换;解码循环加入输出边界检查;对非法字符应报错而非忽略。

04高危问题(High,11 项)

HighH-01设备端RNG(用户重点)
DRBG 熵反馈哈希"尾部余数"而非全部输出 —— 熵积累机制完全失效(三处同源)
Interface/rockey.cc:51(固件)· Interface/dongle.cc:95(主机)· Interface/emulator.cc:661(模拟器)
问题
SHA512(buffer, size, stream) 中的 size 在此位置已被分块循环递减为尾部余量(原始长度 % 64)。请求长度为 64 的整数倍时(生成密钥/nonce 的最常见情况,如 execute.cc:273 的 1024 字节、Ed25519/X25519/uECC 全部密钥生成路径),反馈进 entropy_local_ 的是 SHA512("") ——每次加同一个公开常数,零熵混入。
后果
状态演化 = 已知的计数器自增 + 公开常数 → 给定任一时刻状态,未来全部输出完全确定;DRBG 状态一旦暴露即无法自愈(本设计赖以恢复的 Fortuna 式反馈根本不工作)。详细分析见第 07 节 RNG 专项。
修复:反馈改为对完整输出长度做 SHA512(保存原始长度变量),并周期性混入硬件随机。
HighH-02设备端RNG(用户重点)
RandBytes 超过 128 字节部分 = 陈旧缓冲区内容 ⊕ 密钥流
Interface/rockey.cc:32 · dongle.cc:75(HwARandBytes 只覆盖前 min(size,128) 字节)
问题
硬件随机只填前 128 字节;size > 128 时,[128, size) 区间的"随机数" = 调用前缓冲区残留数据 ⊕ ChaCha20 密钥流。InOutBuf 里通常留着上一次脚本输入/响应(往往是主机可知内容)。
后果
该区间输出的熵与不可预测性完全退化为对 ChaCha 状态的保密性,并与残留数据产生可观察的相关性;1024 字节随机填充(如 app/main.cc 的 Main)命中此缺陷。
修复:硬件随机按 128 字节块滚动注入整个输出区间,或先memset再异或。
HighH-03MCU固件
栈预算仅 2032 字节且无任何溢出保护(README 已知问题的定量化)
MCU/RockeyARM/start.s:6(SP=0x68000BF0)· linker.ld(无栈相关 ASSERT)
定量核算
栈底 0x68000BF0 到 InOutBuf 顶 0x68000400 共 0x7F0 = 2032 字节。Ed25519 Sign/Verify(curve25519.cc:2299/2335/2363/2369/2375)内部创建 240 字节 Sha512Ctx 临时对象,internal_sha512_process 再用 uint64_t W[80] = 640 字节(sha512.cc:230),加上调用链(Start 的 Dongle ~72B + Main 的 VM_t ~300B)总量逼近/超过预算——README 第 28 行承认的"轻微堆栈溢出覆盖 InOutBuf 底部"即此。
其它大栈帧
master.cc:41/196 的 WorldPublic world_public_ 为 1024 字节栈对象;script.cc:818-819(pubk 64B + cipher 256B)、secret.cc:151-153(260B + 256B)同样危险。
后果
溢出向下覆盖 InOutBuf 底部——那里是正在运行的 VM 数据与 RuntimeHeader 副本,造成输出损坏或逻辑错乱,且无检测手段。
修复:大对象移入 ExtendBuf 复用区;链接脚本加栈余量断言;必要时开启 MPU guard page。
HighH-04MCU固件
start.s 从不跳转到 app_entry(依赖链接布局巧合),且不初始化 .bss
MCU/RockeyARM/start.s:20-29 · linker.ld:30
问题(手工反汇编验证)
0x40 起的实际指令序列:LDR r6,[pc,#124] → LDM r0!,{r6,r7}(用 loader 残留的无效 r0)→ LDR r0,=app_entry → 再次 LDM r0!,{r6,r7} → 顺序落入字面池与 .text。全程没有 BX/BLX。当前能工作仅因 app_entry 恰好是 .text 的第一个字节;新增/重排任何对象文件都会让固件从错误地址执行,且无断言保护。
附带
没有 .bss 清零代码,而 linker.ld:30 允许最多 16 字节 .bss——任何落入 .bss 的全局变量将以 RAM 随机值启动。
修复:启动桩显式 LDR r0,=app_entry; BX r0;加 .bss 清零;链接脚本断言 app_entry == _world_start。
HighH-05密码学原语
CHACHAPOLY_Open 先解密后认证 + tag 比较非常量时间
Interface/chachapoly.cc:33-39
问题
(a) 解密在 tag 验证之前完成,认证失败(-EFAULT)时明文已写入输出缓冲且 *size_ 已更新——调用方(VM 指令 kExChaChaPolyOpen,script.cc:1047)收到错误返回值后,VM 内存中仍留有未认证明文,后续指令可读取使用;(b) memcmp 首差异字节短路,对可精确测时的 USB 设备构成可测侧信道,理论上支持逐字节 tag 伪造。
修复:先对密文计算 tag 并常量时间比较(crypto.cc:5385-5388 的 XOR 累加写法现成),通过后再解密;失败时清零缓冲并保持 *size_ 不变。
HighH-06密码学原语
X25519 不检查全零输出 —— 低阶点/小群输入直达密钥派生链
base/src/crypto.cc:4325-4372/5449-5453 · Interface/curve25519.cc:2246-2293 · 使用点 script.cc:1175-1185、execute.cc:368
问题
RFC 7748 §6.1 明确要求接收方检查计算结果是否全零,两条实现路径均未检查;另 fe_frombytes 忽略输入最高位(接受非规范 u 坐标)。
后果
恶意对端提交 Curve25519 已知低阶点可使共享密钥恒为全零或落在小子群内、完全可预测,进而推导下游派生密钥(PREV_MASTER_SECRET 链,execute.cc:368),或通过多次试探缩小本方私钥模小群因子。
修复:在 X25519 出口对 out 做常量时间全零检查并返回错误;两侧实现 + ComputeSecretCurve25519 入口都加。
HighH-07脚本编译器
负数常量立即数编码错误 —— 静默生成错误代码(可执行验证)
Web/Script/lib/grammar.ts:749-757(ConstExpr.Statement 负数分支)
问题
对 value ∈ [-0x100000, -0x1001] 且低 12 位非零的负数,编码把本应减去的低位做成了加法。实测(复刻编译器 + VM 语义模拟):-4097 → -4095、-5000 → -3192、-8191 → -1、-0xFFFFF → -1040385。正数路径与边界值正确,仅该区间出错。
后果
无任何编译告警,脚本正常编译运行但结果错误;若该值用作地址/长度,连带产生越权内存访问判断错误。
修复:低 12 位改用减法编码(或把 imm 编为 M、加 0x1000-L);补一组负数边界单元测试。
HighH-08脚本编译器
编译器完全不建模操作数栈深度(opstk = 16)—— 可生成必然 SIGSEGV 的代码
Web/Script/lib/grammar.ts:820-834(CallExpr.Statement)及全部 codegen 路径
问题
README 明言 opstk 只有 16 个字,但 TS 编译器没有任何栈深度跟踪,唯一检查是 assert(args.length < 16)。实测:4 层嵌套的 5 参调用总代码仅 23 个半字(远小于 100 上限,编译通过),运行期最大栈深 18 > 16 → SIGSEGV,错误路径 memset(data_, 0, kSizeData) 清空全部输入输出数据。
定性
VM 有运行时防护所以不是内存破坏,但属于"编译通过、必然运行失败、失败模式带数据清零"的编译器缺陷。
修复:为每条语句/表达式做静态栈深计算,超限在编译期报错。
HighH-09模拟器
密钥文件写入失败仍提交状态 —— 私钥槽被静默置为"已写入全零"
Interface/emulator.cc:524-548(OpWriteSecretFile)
问题
无论 callback 是否失败,第 546 行 EncryptBuffer 无条件执行;空文件分支中 header.empty_file_ = 0 先于 callback。触发:WriteDataFile 传入越界 offset/size(callback 返回 -ERANGE)或 GenerateRSA 失败——错误码虽返回,但文件已从"未写入"变为"已写入 32/256 字节合法加密的全零内容"。
后果
后续 ReadDataFile 成功返回全零而非报错,"首次写入"状态永久丢失;对密钥文件意味着私钥槽位被静默清空。
修复:callback 失败时回滚状态(不 EncryptBuffer、不落 empty_file_ = 0),直接向上传递错误。
HighH-10模拟器
模拟器打开失败即静默重建并覆盖狗镜像 —— 数据不可逆丢失
src/app/main.cc:646-647 · main.cc:810(Write 无条件执行,"wb" 截断重写)
问题
if (rockey.Open(...) < 0) rockey.Create(...) 对任何失败(文件损坏、SHA 不符、主密钥/口令输错 -EACCES)都落入 Create;执行结束后无论成败都以 "wb" 重写原文件。
后果
口令敲错一次 → 原镜像内全部密钥文件被新空狗覆盖;脚本执行失败时对已部分修改的状态也会落盘。
修复:区分"文件不存在"与"打开失败";打开失败立即退出不落盘;写回前做备份。
HighH-11MCU固件
elf2bin.cjs 静默丢弃除第一个 PT_LOAD 外的所有段
MCU/RockeyARM/elf2bin.cjs:68-84(phnum 校验整段被注释)· 86-95(只取 phdr[0])
问题
链接脚本产生多个加载段(.text@0、.data@0x68000BF0、g_FEI@0x68001400),.bin 只从 phdr[0] 生成,后续段内容不进镜像也无告警。当前靠 linker.ld 的空段 ASSERT 兜住 .data/.rodata,但 g_FEI 段没有任何断言——若未来向 .ARM.__AT_0x68001400 放数据将被静默丢弃,固件行为错误且无法从构建输出发现。
修复:恢复 phnum 校验;对每个 PT_LOAD 输出诊断;g_FEI 段加非空即报错的构建检查。

07设备端随机数发生器专项分析(用户指定重点)

结构:启动时 entropy_local_[16](64 字节)← 硬件 TRNG;之后每次 RandBytes 以 ChaCha20 计数器模式出流(rlCryptoChaCha20Block 为纯函数,不自增计数器),并用 SHA512 输出反馈更新状态。InitializeEntropyLocal(secret.cc:99-106)混入编译期私有常数,构造函数再经 SeedBytes 混入狗信息。

发现汇总(4 项,含 2 高危)

  • High RNG-1 = H-01:熵反馈用循环消耗后的余数 size,64 倍数长度时反馈 SHA512("") 公开常数——熵积累机制整体失效(rockey.cc:51 / dongle.cc:95 / emulator.cc:661 三处同源,系复制粘贴扩散)。
  • High RNG-2 = H-02:超过 128 字节部分 = 陈旧缓冲区 ⊕ 密钥流(rockey.cc:32),输出与 InOutBuf 残留数据产生可观察相关性。
  • Medium RNG-3 = M-12:两处 HwARandBytes 调用不检查返回值;TRNG 失败时 entropy_local_ = 0 ⊕ 编译期常数 → 同批次固件的设备输出完全一致;且启动后从不重播种,叠加 README 已承认的 Ed25519 栈溢出(可能写坏内存),DRBG 状态一旦受损无法自愈。
  • Low RNG-4:计数器仅递增 word[15],32 位回绕后密钥流重复(2^32 块,设备生命周期内实际达不到);同状态内相邻块 nonce 呈 +1 递推(ChaCha 本身安全,仅提示)。
核心判断:该 DRBG 的不可预测性完全依赖启动时那 64 字节硬件随机数——因为反馈失效(RNG-1)、无重播种(RNG-3)、超 128 字节无硬件熵(RNG-2),状态演化对知道初始状态的攻击者是确定性已知的。而项目全部密钥生成(Ed25519/X25519/uECC 密钥对、RSA 会话材料、随机填充)都经过这条路径。

修复建议(按优先级)

  • P0:SHA512(buffer, size, stream) 改用保存的原始长度;三处同源一并修复。
  • P0:size > 128 时硬件随机按 128 字节块滚动注入(或先清零缓冲);检查 get_random 返回值,失败重试并混入 tick 计数器作为最低保障。
  • P1:每 N 次调用或每分钟强制重播种(把 HwARandBytes 直接混入 entropy_local_,经 SHA512 而非加法);可参照 Fortuna 的多池结构。
  • P1:修复 Ed25519 栈溢出(H-03),消除状态被覆写的物理通道。
